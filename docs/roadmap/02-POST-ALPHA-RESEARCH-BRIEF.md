## 4. Chat-log/history and shared gameplay event research

Prefer local saved chat files over OCR, for efficiency, theme independence and compatibility. Prior limited owner log audit reported 14 Battle entries, four wild Pokémon mentions, two status mentions, no detected turn or HP announcements. This is earlier reported evidence, not a new audit and not full battle-state proof. A current community Gym Tracker describes local prize-money line detection and gym cooldowns. Neither proves all earnings, HP, turns or location are available, nor blanket policy approval. Investigate Linux native/Flatpak and Windows client paths, exact settings, log naming/format, encoding, timestamps and channels; Android access separately. Test actual disk output versus visible Battle chat with damage-percent setting on/off, timestamps, EN/ES/ZH, stock and custom strings, Default and Better Default themes. Research logs historically and live, never read or retain unrelated public/private chat or upload raw logs.

Proposed architecture for evaluation, not implementation: opt-in read-only file selection/discovery -> bounded incremental reader -> language-aware parser -> validated normalized gameplay events (source, confidence, timestamp, profile, session, battle, stable id, parser version) -> SQLite event store with deduplication and manual corrections -> existing services/API/event bus -> optional tool integrations. Explore per-file offsets, file identity/rotation/truncation, partial lines/UTF-8, timezone/DST/day boundaries, duplicate historical imports, replay, reconnect, simultaneous clients, character attribution, unknown strings, stale/disconnected state, contradictory events, bounded work, migration/rebuild, deletion/export, privacy minimization and opt-out. First sync should not fire historical alerts. No hidden information, exact inferred values presented as observed, game process/memory/packets, injection, automated inputs, screen/control automation, anti-cheat bypass or reading other apps' private files. Seek written staff clarification on passive tracking and real-time battle assistance (especially PvP) before release; restrict scope where required. Research-only permission is not game policy approval.

Collect controlled sanitized fixtures only with user consent: wild single, trainer, double, 3/5 horde, alpha, capture success/failure, balls/HP/healing/status/moves/abilities/weather/turns, switches/fainting, EXP/EV and level events, Pay Day/Pickup/Thief, gym/E4/trainer payouts and requirements, berry planting/watering/harvest, eggs/evolutions, storyline events, location/region, relog/alt switch, restart and midnight rotation. Establish baseline and golden parser/negative fixtures with synthetic anonymized examples; do not assert exact catch/HP/position/account balances/complete inventory from partial events.

## 5. Tool-by-tool research, especially live capture and economy

Investigate how to enhance existing workflows before adding new navigation. For each proposed feature provide actual source/evidence, manual mode, reliable automatic inputs, missing data, uncertainty, policy constraints, UX and popout/mobile behavior, shared service/data model, cost/complexity, dependencies, acceptance tests and value relative to user feedback.

- Catch calculator: audit companion/services/calcs.py and tests independently of tracking. Current Gen III/IV-style four-shake estimates and conditional multipliers have unconfirmed cases, exclude Alpha/raid/Legendary special capture rules. Verify PokeMMO-specific ball multipliers, HP and rounding/shake model, status/turn/environment, caught-before/species attributes, Safari/Alpha exceptions. Compare current official changes, in-game descriptions and reproducible evidence. Investigate live/manual modes and only fill verified fields (species, level, revealed status, turns, balls, HP or damage if available); unknown HP means manual input or clearly bounded estimate, unknown turn/conditions not a favorable default. Never guarantee accuracy or recommend actions automatically. Offline calculator remains useful.
- Battle reference: possible observed opponent species/types/moves/revealed ability/status, type chart, current Pokémon lookup, manual HP, observed weather/effects and timers; no hidden moves/IVs, false precision, real-time PvP recommendations or damage simulator. Comparison remains main-page unless approved. Determine policy and technical feasibility of a dedicated compact Battle Companion vs existing tool panes.
- Pokéyen and economy: daily/weekly/monthly activity on customizable Home; detailed optional activity/economy workspace only if justified. Prize money, gym/trainer/E4, farming, loot, expenses, manual corrections, realized sales versus estimated unsold loot, net recorded cash flow/profit per hour and goals. Check which messages are actually logged (Pay Day, item sales, GTL, fees, consumables, charm effects, trades, mail, purchases). Do not call partial recorded flows wallet balance or true total profit; reconcile manually and avoid double-counting. Keep historical imports, time zones, multiple profiles and account-specific totals separate. Don't count encounters/shiny odds.
- Progression: integrate confirmed trainer victories and cooldowns into existing repeatable custom guides, timers, teams, notes, optional manual/reversible step suggestions. Gym/E4 and trainer-rematch rules must be verified. No automated inputs. EV/EXP training goals link Box, team, location, yield and modifier data; exact EV/EXP/participation requires evidence or manual confirmation.
- Pokédex/collection: advanced reference filters, held-item/egg-group/EV/move finder, manual or confirmed registrations; prompt to save important catches only, do not create Box entry for every wild encounter or catch. Optional fields, original trainer, forms/costumes/shiny/secret shiny/alpha, notes/photos/tags, team and Showcase links. Keep current reference catalog distinct from obtainable roster and personal progress.
- Location and items: improved location filters, EV/EXP/held-item opportunities, personal location observations, bookmarks, loot lists, crafting/shopping, authorized price reference; named location only if actually observed, no coordinates or interactive map revival without approval. No invented inventory quantities or unauthorized market scraping.
- Guides/timers, teams, breeding and berry projects: shared repeatable routines and cooldowns, reusable teams for catching/reruns/raids/storyline, training projects, verified breeding costs/inheritance/egg moves, optional berry plots/harvest/manual logs. No assumption of access. OCR only secondary for gaps that justify it, local opt-in, Default/Better Default, scaling and KDE screen portal, explicit policy approval. Never bypass permissions. Keep lightweight and manual-first.

## 7. Profiles, accounts, cross-device progress and synchronization research

Owner wants easy switching between main/alt game accounts and characters and cross-device notes/progress eventually; no PokeMMO credentials or access to actual game accounts. Explore a local-first profile model separately from optional Companion cloud identity: local install/device -> optional Companion sync account -> user-defined game account labels -> character/profile with stable UUIDs -> scoped data; allow multiple local profiles without login, shared notes/teams versus character-scoped entries, global vs device-specific preferences. Audit existing guide-run IDs, Box, dex registration, legendary catches, notes links, backups, documents, bookmarks, timers, settings and foreign keys before designing migrations. No destructive resets or automatic assumptions linking same-name characters. Profile switching across all tools should be obvious, reversible, and preserve old data. Separate reference data and user data, app account and PokeMMO account, device and profile identity, manual ownership and observed events. Define export, import, merges, duplication, account unlink/delete, recovery and shared content behavior.

Evaluate levels: manual versioned ZIP export/import (existing backup service as starting point, validation and preview, Merge/Replace and safety backup); optional local LAN/peer sync with authentication and pairing; managed sync backend with Cloudflare Workers/D1/R2 as previously preferred candidate; compare Supabase/Postgres/Auth, Firebase, self-hosted home server/low-resource hardware and other appropriate low-cost managed options. Recheck live quotas and terms from official sources: https://developers.cloudflare.com/workers/platform/pricing/ ; https://developers.cloudflare.com/d1/platform/pricing/ ; https://developers.cloudflare.com/d1/platform/limits/ ; https://developers.cloudflare.com/r2/pricing/ . Don't promise unlimited/free hosting; model 100/1,000/10,000 active users and realistic device count, records/day, reads/writes, indexed queries, attachments/storage/egress, request/CPU limits, auth/email cost, backup retention and operational workload. R2 for optional media, D1 for structured data only if fit demonstrated; no raw chat logs in cloud. Avoid whole SQLite live-file replication over generic drive folders. Assess local SQLite source of truth, outbox/change journal, per-record UUIDs and revisions, idempotency, tombstones, delta cursor, per-device metadata, conflict detection (notes conflicts not silent last-write-wins; sets/progress semantics and deletion handling), schema/version compatibility and migration, retries/backoff, offline edits, duplicate event dedupe, clock skew, sync snapshots, backups and rollback. Compare server-readable vs end-to-end encrypted data, account recovery/key loss, TLS, auth token secure storage, per-tenant authorization, access control tests, rate limits, account deletion/export, minimal analytics, GDPR/privacy, provider lock-in and service outages. No activation keys, forced login, paywall or mandatory online service. Never store game login credentials. Sync only user-approved records; raw logs/private chat, platform-specific window bounds and secrets stay local. Attachments/screenshots optional with clear quotas, user controls, and no unnecessary transfer. Research optional PC-to-phone derived daily activity, notes, guide progress, Pokémon records, goals, teams and settings with per-entity sync semantics; separate immutable reference version. Website/public profile and Discord account link only future ideas, not prerequisites. Account stats/pokeyen recorded values should be private by default.
