# Live Catch Rate, theme calibration and Events — research handoff
**Date:** 2026-11-27. **Status:** Research only; no implementation, roadmap, version, merge or release approval. Owner requested documentation on GitHub and an offline ZIP. Baseline develop: 1108e24fa64461a4af9010012624a2e3472e0ac0. Companion is an offline-first Python/SQLite/local HTTP/JS/PySide6 application for Windows and Linux.

## 1. Scope and owner decisions
Focus on a durable optional live catch-rate tool and a clean forum Events browser. Use OCR/computer vision AND saved battle logs together, not competing mutually exclusive modes. Default and Better Default are first-class supported theme families; ordinary users can adjust every detection region. Support single, double, 3 and 5 opponent layouts from the data model onward. Do not hardcode the uncertain 5-horde row arrangement. Keep manual mode and existing popouts. Floating quick-access toolbar remains a separate future idea. Defer the full Developer Studio, broader log integration, Android, global admin/backend, advanced PvP analysis and community publishing. No encounter counter. Preserve existing Statistics-first decisions; this document does not supersede release plans.

It offers offline image analysis. This is a comparator, not proof of PokeMMO endorsement or correctness.
- Its forum discussion [S2] contains a report of repeated CPU spikes to 100%, audio glitches and stutter. Previous research also noted high CPU and theme/UI-scale complaints. Direct thread returned HTTP 403 on this pass; indexed excerpt confirmed the CPU report. Do not treat reports as reproducible measurements or assume a root cause. Issues and calibration file [S3, S4] are useful research references. No license file visible in root listing: no copying or redistribution of code or assets without verified permission/license.
- Private owner logs (November 24 export; do not commit raw logs, names or private chat): wild species, active Pokémon, turn number, damage percentages, move use, sleep, faint/escape, confirmed catches and trainer payouts were observed. One False Swipe removed 98.5% of opponent HP; 1.5% remains only if it began at full HP and no other changes occurred. Another battle records Oran Berry recovery without a quantity. Therefore logs alone cannot establish exact HP. Multiline records and different date formats are present. Ball acquisition messages do not establish which ball was thrown. No proven live write latency, complete capture state or exact opponent level from these samples.

Assuming full starting HP, 26.8% reconciles with the visual bar. Screenshot shows only a displayed estimate; neither its odds nor underlying game formula independently verified.

Three-Zorua and five-Metang/Flaaffy examples demonstrate distinct arrangements; Shiny Gloom nameplate text and localized Flaaffy level labels are useful fixtures. Therefore one fixed RGB threshold is insufficient even within Better Default. Test Default and Better Default independently, with both backdrops, high-contrast bars, multiple palettes/custom HP colours and UI scaling.
- Official Shiny Wars 2026 changelog [S10] adds catch rate to Pokédex summary. Older staff statement [S11] describes Gen 3/4 formula and Gen 5 base rates; later community discussion [S12] questions rounding/scaling. The exact current server algorithm is unverified. Community reports [S13] warn of apparent 100% estimates failing; never promise guaranteed outcomes based on an estimate.
- Official policy [S14–S16] restricts unfair-advantage tools. Ask staff about passive live capture assistance and logs before release or live gameplay testing; do not infer approval from other tools.

## 3. Hybrid architecture and reliability
Capture-only service, not a whole-app tracking overhaul: read-only local log tail -> locale-aware parser -> timestamped battle events; OS-approved window capture -> changed regions -> targeted OCR and cheap image processing; both -> battle reducer/reconciler -> versioned catch calculator -> existing page/popout. Each observation carries source, time, battle generation, slot, confidence and freshness. Manual corrections take precedence for the current battle and can be reset. OCR and logs actively corroborate each other. Do not let a delayed log overwrite a newer observation. Track unknown values explicitly.

Log tail: opt-in, user selects supported log folder; incremental byte offset, partial writes, multiline messages, rotation/truncation, duplicate detection, locale-aware timestamp normalization, session/character boundaries. Ignore public/private chat and unrelated channels; no raw uploads. Reset on session change, log gap, lost game window or uncertain battle boundary. Use species dictionary and aliases from approved reference data; game language independent of Companion UI language. Tests EN/ES/ZH; no language claims until validated. No automatic chat-log configuration changes.

Visual path: only consented game window/screen source; crop to HUD, never capture unrelated windows deliberately; never inject, read memory, intercept packets or send inputs. Use fixed/anchor-relative regions for name/level, status icons, HP fill, caught/alpha/shiny marks, battle/menu indicators, location/time only if needed. Avoid sprite recognition (sprite/ROM mods change visuals). Use OCR for names/levels and text, CV for HP geometry, template/colour recognition, inexpensive change hashes for triggering; don't OCR health bars. No persistent frames unless user opts into diagnostic export. Separate platform capture adapters: Windows windowed/borderless; Linux X11 and Wayland separately. Qt documents Wayland portal/PipeWire requirements and user selection [S17]; actual KDE permission, minimize, resizing, monitor and overlay behavior untested. Avoid recursive capture of own overlay; position outside selected ROI or use supported capture exclusion. Stop on revoked permission.

State machine: disconnected -> idle/overworld -> battle candidate -> recognized active battle -> transition/animation -> stable -> ended/stale. Track original layout vs survivors. Capture slot identity uses stable HUD anchors and battle generation, not species alone. Same-species horde damage or status messages may not identify which slot; reconcile only if unambiguous or mark pending. A five-slot encounter narrowing to three remains a five-slot layout unless observed UI transition establishes remapping; never automatically equate live count to original layout. Fainted slots retain state, don't migrate HP/status to another. Wait for animations to settle; use bounded retries and temporal consensus, then ask for correction. Disable stale odds, show explicit unknown/unsupported, never carry prior battle values forward. Only show per-ball rates when exactly one eligible target remains under verified rules; trainer/PvP/raid/unsupported modes must not produce misleading odds. Confirm wild doubles, mixed hordes, faint transitions and actual catch eligibility against current game.

Reconciliation examples: log says damage -73.2%, visual HP 27%, accept agreement within measured rounding tolerance; log announces unknown heal, invalidate HP estimate and refresh bar; log has two identical names, don't arbitrarily assign damage; log sleep + visual SLP agree, increment sleep duration only on validated turns; missing level -> OCR/manual; OCR name conflict -> normalize against catalog, recheck, don't silently guess. Confidence is field-specific, not a single misleading aggregate. User-facing compact panel shows stale/uncertain state and manual override.

## 4. User calibration — no fixed HUD coordinates
Ordinary Settings -> Live Catch Rate -> Calibration, no developer access required. Guided still capture of current game; draw/move/resize/add/remove independent boxes with zoom, keyboard nudge, numeric coordinates, undo/reset. Profile contains schema/version, theme/version, client build, platform, client language, DPI/UI scale, window aspect/size family, battle HUD size, anchor strategy, slot count, each named region and algorithm parameters (HP fill thresholds/geometry, templates, contrast/thresholding, recognition limits). Store normalized coordinates relative to captured client content and validate aspect/anchors; arbitrary stretching is not safe. Allow separate regions per slot and per field. Save original single/double/3/5 profile plus transitions; custom layout creation. Automatic suggestions optional; manual always available. Detect mismatch on theme/scale/window changes; invalidate calibration rather than silently using wrong regions. Export JSON profile only (no screenshots, usernames, paths or private logs); schema validate and limit sizes, no executable code. Allow user/community presets but mark unverified. Bundled profiles require evidence and versioning.

Default + Better Default are mandatory initial QA targets, not already working. Test 13 Better Default presets (at least full cross-preset critical HP/status smoke checks), high contrast, customized bar colors, both backdrop options, dark/light contrast, Better Items icon mod on/off where relevant, both available desktop battle HUD sizes where applicable. Use actual current clean Default and matching Better Default 1.8.0 assets supplied/authorized by owner for template exploration; don't assume all customized instances match. Need screenshots at full/native resolution, no cropping that destroys HUD anchors. No automatic edits to installed themes. Future theme versions: compare asset/layout changes, rerun fixture suite, version profiles independently.

## 5. Performance engineering — benchmark before shipping
No OCR when off, disconnected or minimized; start worker lazily and stop on disable. One bounded worker shared by tool and popouts, reuse model, latest-frame-wins queue (capacity 1), coalesce events, drop stale jobs, watchdog restart with backoff, no busy polling or spin. Use cheap pixel difference first; cache names/levels until encounter changes; HP CV only for active slots; only OCR changed ROIs. Proposal: Eco 1 visual check/s, Balanced 3, Fast 5; these are upper bounds for cheap checks, NOT OCR calls per second. Min OCR interval 1s initially, triggered by changed region or log event; separate slower location check if needed. Default 1 OCR worker thread; optionally 2 after benchmark. ONNX Runtime documents intra/inter-op pools and spinning [S18]; compare sequential mode, limited intra-op threads, spinning disabled, OpenCV thread cap; possible contributors, not established causes of ShakeChecker spikes. Prioritize smooth gameplay, back off under load, emergency pause, do not require GPU. Compare RapidOCR/ONNX, Tesseract for constrained text, and game-font/digit recognition where licensed. Select by measured accuracy/latency/CPU and model license, not hype. CPU use reported as percentage of total system capacity and core equivalents; compare game-only baseline.

Proposed acceptance targets (not measurements): idle incremental CPU <1 percentage point; ordinary gameplay average <3; active battle average <5; p95 recognition latency <=1s after stable state; no growing queue; disabled worker absent; no reproducible audio interruption; compare frame-time p95/p99 and 1% lows, CPU peaks, GPU, RSS and sustained thermal load. If target missed, slow down or disable live mode on affected hardware; never quietly degrade accuracy. Test on low/mid-range Windows/Linux systems (including owner's older i5 and current desktop if available); 720p/1080p/1440p, scaled/multi-monitor, resizing/moving/minimizing, 30–60 minute soak and rapid consecutive battles. Measure capture vs preprocessing vs inference vs UI separately. No live benchmark has been performed.

## 6. Catch mathematics and UI
Versioned mechanics manifest: source/build/date, base species/form rate, conditional ball factors and rounding, HP range, status, turn, sleep duration, encounter type, local game time/cave, ownership and any verified chain rules. Treat raw rate vs Pokédex displayed percentage as different fields. Do not assume Repeat Ball is a chain or ordinary caught flag without current verification; likewise Dream, Timer, Quick, Dusk, Nest, Net, Alpha, roaming legendary, Safari, special event mechanics. Establish official values where possible and independent reference comparisons; finite sample outcomes cannot establish exact server formula. Use validated mathematical unit vectors, rounding boundaries, max HP/1 HP, missing inputs, unsupported species/forms and controlled observations. No false certainty or 100% estimate unless a verified guaranteed rule; output approximate odds, ranges or unavailable. No automated input or action selection. Manual calculator always available offline; live tool opt-in. Compact/Standard/Expanded, selectable ball list and sort, local settings, per-field overrides, source/freshness indicator, HP/status/level/turn and eligible target. Link to existing Pokédex and item references; no encounter tally. The user's priority is reliable capture odds, not recreating ShakeChecker's location dex now.

## 7. Events page — intentionally simple
One page with All, Official, Unofficial, PvP, Seasonal filters/tabs; source authority and activity category are separate axes (an unofficial PvP tournament is both). Upcoming/ongoing/past, search title/species/reward, chronological view, local time conversion with original timestamp and timezone. Card shows title, organizer, category, start/end/duration if known, region/location or in-game signup, primary prize and sprite. Detail shows concise rules, eligibility, scoring, signup, all prize placements, original forum link. Use existing licensed/bundled sprites: shiny reward uses shiny variant, normal uses normal, item uses item icon, RP/Pokéyen amount, cosmetic fallback if no asset. Do not assume prize is shiny or Alpha; explicit flags only. PvP tab is events only (OU/UU/NU/Doubles/Randoms/team formats as published), no ladder, damage calculator or live tactics. Seasonal featured cards only when announced; Christmas dates around Dec 24/25 and Lunar New Year around Feb/Mar are expectations, not confirmed 2026/27 dates. Halloween history separately archived. No scoring tracker or event registration automation required.

Forum index [S19] exposes Official/Unofficial and Chinese events plus seasonal material. Official OU Golden Treats example [S20] has a shiny Sableye prize and 1,300 RP; use to test prize parsing, not an upcoming event. Community event discussion [S21] illustrates varied formats. Ingestion investigate permitted RSS/public feed/API and rate limits/robots/terms; some direct pages 403. Do not bypass blocks or automate login. Prefer cache, conditional requests, modest refresh interval, backoff, dedup by stable thread ID, revision hash/edit detection, status updates for postponed/cancelled events, source timestamp and last successful refresh. If blocked/offline display cached content with age; manual source entry/import or link-only fallback. Avoid making a backend mandatory; optional shared curated feed only after separate approval. Don't reproduce full copyrighted posts/artwork; summarize facts with attribution, link original, use existing permitted assets. Unknown fields null, not invented. Preserve source title/time strings, timezone ambiguity, reward quantities, tie/placement groups, language and organizer. Sanitize HTML; external links open system browser; no forum credentials. Tests for malformed posts, multi-day, DST, dates in title vs actual start, edits, mixed rewards, no prize, duplicates, unofficial PvP and archive.

## 8. Proposed validation gates (not a development authorization)
A: Staff clarification, current screenshot/log fixture collection and independent capture formula review.
B: Offline replay spike: same screenshot/log timeline; compare OCR-only, log-only and hybrid accuracy/coverage and resource use; no game integration required. Build ground truth per slot incl levels, HP tolerance, status, turn, layout and eligibility. Use precision/recall, exact-match and unknown/false-positive counts; split holdout by theme/scale, report confusion matrices. Prioritize false positives over coverage; no odds on ambiguous target. Validate all 1/2/3/5 types with partial fainting, duplicate species, mixed levels, shiny/alpha, status, healing, weather, residual damage, lost logs, late messages and resize.
C: Calibration UX prototype and cross-platform capture permission tests; profile export/import round-trip; no hardcoded layout.
D: Only if approved, integrate capture-specific service into existing Companion; benchmark before release. Separately test event parser on permitted official/unofficial/PvP fixtures, cache and source fallback. No version bump, code, PR, merge or release from research alone.
